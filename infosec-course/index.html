1.1 SQL Injection: Абстрактное синтаксическое дерево (AST) и 5 классов инъекций

MITRE T1190 CWE-89 ФУНДАМЕНТАЛЬНАЯ ТЕОРИЯ
Архитектура обработки SQL-запроса в ядре СУБД

В основе любой реляционной СУБД (PostgreSQL, MySQL, SQLite, Oracle) лежит многостадийный транслятор запросов:

1
Лексический анализ (Lexer / Tokenizer): Преобразует исходную строку SQL в поток токенов (ключевые слова SELECT, идентификаторы полей, строковые литералы, операторы).
2
Синтаксический анализ (Parser): Строит Абстрактное Синтаксическое Дерево (AST — Abstract Syntax Tree), проверяя соответствие грамматике SQL (BNF).
3
Оптимизатор запросов (Query Optimizer): Формирует план выполнения (Execution Plan), выбирая индексы (B-Tree, Hash), типы соединений таблиц (Nested Loop, Hash Join) и предикаты.
4
Движок исполнения (Execution Engine): Считывает страницы данных с диска или из Buffer Pool и возвращает результат.

Фундаментальная причина уязвимости (Root Cause): При использовании конкатенации строк (например, f"WHERE title = '{user_input}'") пользовательские данные попадают в фазу Лексического и Синтаксического анализа. Если ввод содержит метасимвол кавычки ('), лексер завершает токен строкового литерала, а последующие слова (OR, UNION, SELECT) распознаются как новые операторные узлы в AST. Это изменяет структуру самого алгоритма исполнения!

Математика бинарного поиска в Blind SQL Injection

При слепом посимвольном извлечении данных (Boolean-based) перебор каждого символа ASCII таблицы (128 значений) последовательно потребовал бы в среднем 64 HTTP-запроса на символ. Использование алгоритма бинарного поиска (метод деления отрезка пополам) сокращает число запросов до логарифмической сложности:

Количество запросов на символ = ⌈log₂(128)⌉ = 7 запросов.
Для строки пароля длиной 32 байта: 32 × 7 = 224 HTTP-запроса вместо 4096!
Протокольный механизм Prepared Statements

Настоящие параметризованные запросы (Prepared Statements) работают через специальный бинарный протокол СУБД (например, в MySQL команды COM_STMT_PREPARE и COM_STMT_EXECUTE):

  • Клиент отправляет шаблон: SELECT * FROM users WHERE login = ? AND pass = ?. СУБД однократно компилирует AST и генерирует план запроса. Места под параметры помечаются дескрипторами типов.
  • Клиент отправляет значения параметров по бинарному протоколу. Они вставляются непосредственно в ячейки памяти уже скомпилированного плана. Никакая часть входных данных в принципе не может быть интерпретирована как SQL-код, даже если содержит кавычки, точки с запятой или комментарии.

1.2 SSRF: Стандарт Link-Local (RFC 3927), IMDSv1/v2 и механика DNS Rebinding

MITRE T1552.005 CWE-918 CLOUD & ENTERPRISE
Архитектура Link-Local адресации и Cloud Metadata

По спецификации RFC 3927 блок адресов 169.254.0.0/16 зарезервирован для автоконфигурации сетевых интерфейсов в локальном сегменте (Link-Local / IPv4LL). Пакеты с такими адресами не подлежат маршрутизации через шлюзы.

Все ключевые облачные провайдеры (Amazon Web Services, Google Cloud Platform, Microsoft Azure, OpenStack, DigitalOcean) используют виртуальный сетевой стек гипервизора (KVM, Nitro, Hyper-V) для перехвата обращений к адресу http://169.254.169.254/. Этот сервис называется Instance Metadata Service (IMDS).

Сравнительный анализ IMDSv1 и IMDSv2
Критерий IMDSv1 (Уязвимый стандарт) IMDSv2 (AWS Session-Oriented Hardening)
Метод запроса Простой GET запрос к эндпоинту. Обязательный двухэтапный протокол с методом PUT.
Аутентификация Отсутствует. Доступ открыт любому процессу на хосте. Требует сессионный токен в заголовке X-aws-ec2-metadata-token.
Уязвимость к SSRF Критическая. Любой базовый SSRF в веб-приложении мгновенно извлекает секреты IAM-роли. Защищен. Большинство SSRF эксплойтов не могут отправлять произвольные методы (PUT) и кастомные HTTP-заголовки.
Сетевой TTL пакета Не регламентирован. По умолчанию IP_TTL = 1 на ответных пакетах токена, что блокирует прохождение через промежуточные reverse-proxy и контейнерные шлюзы.
Анатомия атаки DNS Rebinding (Обход белых списков и фильтров IP)

Многие разработчики внедряют наивную защиту: резолвят полученный домен в IP, и если IP не является приватным, выполняют HTTP-запрос. Механика DNS Rebinding эксплуатирует разницу во времени между проверкой и использованием (Time-of-Check to Time-of-Use — TOCTOU):

1
Атакующий регистрирует домен (например, rebind.attacker.com) и поднимает собственный авторитетный DNS-сервер.
2
На первый запрос резолвера (проверка в коде приложения) DNS-сервер возвращает легитимный публичный IP: 198.51.100.1 с TTL = 0 секунд (запрет кэширования).
3
Приложение считает адрес безопасным и вызывает requests.get(). Так как TTL истек, библиотека выполняет повторный DNS-запрос.
4
DNS-сервер атакующего на второй запрос возвращает приватный адрес: 169.254.169.254 или 127.0.0.1. Запрос отправляется на закрытый внутренний сервис!

# SECURE: Комплексный валидатор: валидация схемы, фиксация IP и защита от DNS Rebinding
import socket
import ipaddress
from urllib.parse import urlparse

def safe_http_fetch(url):
    parsed = urlparse(url)
    if parsed.scheme not in ('http', 'https'):
        raise ValueError("Разрешены только протоколы HTTP и HTTPS")
        
    hostname = parsed.hostname
    port = parsed.port or (80 if parsed.scheme == 'http' else 443)
    
    # 1. Резолвим IP адрес хоста
    addr_info = socket.getaddrinfo(hostname, port, family=socket.AF_INET, type=socket.SOCK_STREAM)
    target_ip_str = addr_info[0][4][0]
    target_ip = ipaddress.ip_address(target_ip_str)
    
    # 2. Проверяем диапазоны: запрещаем Private (RFC 1918), Loopback (127.0.0.0/8), Link-Local (169.254.0.0/16)
    if target_ip.is_private or target_ip.is_loopback or target_ip.is_link_local or target_ip.is_reserved:
        raise PermissionError(f"Доступ к внутреннему IP запрещен политикой безопасности: {target_ip}")
        
    # 3. Защита от DNS Rebinding: запрос отправляется НАПРЯМУЮ на проверенный IP адрес,
    # а имя исходного хоста передается строго в заголовке Host!
    safe_url = f"{parsed.scheme}://{target_ip_str}:{port}{parsed.path or '/'}"
    headers = {"Host": hostname}
    return requests.get(safe_url, headers=headers, timeout=3, allow_redirects=False)

1.3 Race Conditions: ACID транзакции, феномен TOCTOU и атака HTTP/2 Single-Packet

MITRE T1068 CWE-362 КОНКУРЕНТНОСТЬ & СЕТИ
Теоретические основы: ACID и уровни изоляции транзакций

В многопоточных и распределенных системах любая бизнес-операция взаимодействия с базой данных должна соответствовать критериям ACID:

  • Atomicity (Атомарность): Транзакция фиксируется полностью (Commit) или не выполняется вовсе (Rollback).
  • Consistency (Согласованность): База данных переходит из одного корректного состояния в другое, не нарушая инвариантов бизнес-логики.
  • Isolation (Изоляция): Параллельно исполняемые транзакции не должны оказывать взаимного влияния.
  • Durability (Долговечность): Зафиксированные изменения гарантированно сохраняются на энергонезависимом носителе.

Феномен TOCTOU (Time-of-Check to Time-of-Use)

Уязвимость Limit Overrun возникает при паттерне Check-then-Act: приложение считывает значение баланса в память процесса веб-сервера, проверяет условие (balance >= price) и затем выполняет запись. В интервале времени между чтением и записью (окно конкурентности) другие потоки веб-сервера успевают прочитать то же самое старое значение баланса!

Физика сетевой атаки HTTP/2 Single-Packet Attack

Раньше для эксплуатации гонок состояний требовалось отправлять десятки TCP-пакетов одновременно, однако джиттер задержки сети (Network Jitter в 5-20 мс) рассинхронизировал их приход на сервер. Техника HTTP/2 Single-Packet Attack использует мультиплексирование потоков HTTP/2: атакующий упаковывает 20–30 независимых HTTP-запросов (Stream Frames) в один-единственный физический TCP-сегмент размером до MTU (1500 байт). Сетевая карта сервера принимает этот пакет, распаковывает кадр и передает все 30 запросов в ядро ОС в один и тот же такт процессора (джиттер < 100 наносекунд), гарантируя победу в гонке состояний!

Анатомия JSON Web Token (RFC 7519 / RFC 7515)

Структура токена JWS (JSON Web Signature) состоит из трех частей, разделенных точками: Header.Payload.Signature:

  • Заголовок (Header): Содержит служебные метаданные сериализации ({"alg": "RS256", "typ": "JWT", "kid": "key-2026"}).
  • Полезная нагрузка (Payload / Claims): Содержит утверждения о субъекте (RFC 7519 Standard Claims: sub — идентификатор, iss — эмитент, exp — срок годности Unix timestamp, aud — аудитория, nbf — не ранее чем).
  • Криптографическая подпись (Signature): Результат вычисления криптографической функции над строкой Base64URL(Header) + "." + Base64URL(Payload).
Математическая суть атаки Key Confusion (Algorithm Confusion)

Разница между асимметричной схемой RS256 и симметричной схемой HS256 фундаментальна:

RSA Signature (RS256):
Подпись (приватный ключ d): S = Hash(M)ᵈ mod n
Верификация (публичный ключ e): Hash(M) ≟ Sᵉ mod n

HMAC Signature (HS256):
Подпись и верификация (общий секрет K): HMAC(K, M) = H((K ⊕ opad) || H((K ⊕ ipad) || M))

При атаке Key Confusion атакующий подменяет заголовок на "alg": "HS256". Если библиотека валидации написана некорректно и не имеет жесткого белого списка алгоритмов, она вызывает функцию проверки HMAC, передавая в качестве секретного пароля $K$ сохраненный на сервере открытый ключ public.pem! Так как открытый ключ сервера общедоступен, атакующий берет строку открытого ключа и локально подписывает любой произвольный payload алгоритмом HMAC-SHA256. Сервер сверяет хэш — и подпись сходится на 100%!

Уязвимость алгоритма "none" (RFC 7515 Section 8.5)

Спецификация JWS допускает токены без подписи (для сред, где целостность гарантируется каналом связи TLS). Если заголовок содержит {"alg": "none"}, а сигнатура пуста (eyJhbGciOiJub25lIn0.Payload.), наивный парсер считает токен доверенным, пропуская этап верификации.

Анатомия протокола ARP (RFC 826)

Протокол разрешения адресов (Address Resolution Protocol) работает на стыке L2 (Ethernet) и L3 (IPv4). Его задача — сопоставить 32-битный логический IP-адрес с 48-битным физическим MAC-адресом сетевой карты.

1
ARP Request (Широковещательный Broadcast): Хост А рассылает по MAC-адресу ff:ff:ff:ff:ff:ff кадр: «У кого IP 192.168.1.1? Сообщите 192.168.1.50».
2
ARP Reply (Одноадресный Unicast): Хост с запрошенным IP формирует ответ: «IP 192.168.1.1 находится на моем MAC-адресе 00:11:22:33:44:55».

MITRE T1046 СПЕЦИФИКАЦИЯ TCP
Конечный автомат состояний протокола TCP (RFC 793)

Протокол TCP обеспечивает надежную доставку потока байтов и представляет собой детерминированный конечный автомат (FSM — Finite State Machine).

1
LISTEN → SYN-SENT: Клиент отправляет флаг SYN со случайным начальным номером последовательности (ISN — Initial Sequence Number).
2
SYN-SENT → SYN-RECEIVED: Сервер подтверждает получение флагом ACK (ISN + 1) и отправляет собственный SYN.
3
SYN-RECEIVED → ESTABLISHED: Клиент подтверждает получение флагом ACK. Соединение зарегистрировано в таблице сокетов ОС.

2.3 DNS Безопасность: Атака Дэна Камински (Kaminsky Bug), энтропия Шеннона и DNS Tunneling

MITRE T1071.004 CVE-2008-1447 СЕТЕВАЯ КРИПТОГРАФИЯ
Архитектура DNS и уязвимость кэширующих резолверов (Dan Kaminsky Attack)

Протокол DNS (RFC 1035) работает поверх ненадежного протокола UDP (порт 53). В оригинальном стандарте для подтверждения того, что ответ пришел от легитимного авторитетного сервера, использовалось единственное 16-битное поле — Transaction ID (TxID). Общее пространство возможных значений составляло всего $2^{16} = 65536$ вариантов.

В 2008 году Дэн Камински показал, как обойти защиту кэширования: атакующий запрашивает у резолвера несуществующий случайный субдомен (random1.bank.com, random2.bank.com). Резолвер отправляет запрос к авторитетному серверу, а атакующий одновременно посылает лавину поддельных UDP-ответов со всеми 65536 возможными TxID, вкладывая в секцию Authority поддельную NS-запись: «Авторитетным сервером для всей зоны bank.com является ns.attacker.com». Как только один из 65536 ответов угадывает TxID, резолвер отравляет кэш для всего домена целиком!

Современный стандарт защиты (Source Port Randomization): Резолверы обязаны рандомизировать не только 16-битный TxID, но и 16-битный исходный UDP-порт клиента. Энтропия поиска возрастает до $2^{16} \times 2^{16} = 2^{32} \approx 4.29 \times 10^9$ комбинаций, что делает перебор по сети физически невозможным.

Механика скрытого туннелирования данных через DNS (DNS Exfiltration)

Поскольку DNS необходим для работы сети, UDP-порт 53 практически всегда открыт на исходящий трафик даже в самых изолированных корпоративных сегментах. Вредоносное ПО кодирует конфиденциальные данные (хэши, документы) в Base32/Base64 и запрашивает доменные имена:

Схема запроса: [Base32(Секретные данные)].c2.attacker-controlled-domain.com
Пример: JBSWY3DPEBLW64TMMQ.exfil.evil.net

Локальный корпоративный резолвер не знает ответа и пересылает запрос по цепочке к авторитетному серверу evil.net, принадлежащему атакующему. Атакующий декодирует строку из логов DNS-демона, не устанавливая прямого TCP-соединения с жертвой!

Математика обнаружения через энтропию Шеннона

Легитимные доменные имена (например, mail.google.com, api.github.com) обладают низким уровнем хаотичности символов. Закодированные данные (Base64/Hex) имеют высокую статистическую энтропию по формуле Шеннона:

H(X) = - ∑ P(xᵢ) × log₂(P(xᵢ))
Легитимный трафик: H(X) обычно находится в диапазоне 2.2 – 3.2 бит/символ.
Туннелирование / Эксфильтрация: H(X) превышает 3.8 – 4.5 бит/символ + длина метки поддомена > 30 символов.
Используйте ключевые слова dns.query и операторы регулярных выражений pcre.
alert dns any any -> $HOME_NET 53 (msg:"SUSPICIOUS Long DNS Subdomain Exfiltration Query"; dns.query; pcre:"/^[a-zA-Z0-9_-]{45,}\./"; classtype:bad-unknown; sid:2000030; rev:1;)

CAP_SYS_ADMIN «Новый root»: монтирование файловых систем, управление namespaces, BPF. Монтирование дисков, побег из cgroups, замена системных структур ядра, перехват системных вызовов. Critical
CAP_SETUID Разрешает произвольное изменение UID процесса. Вызов setuid(0) из кода интерпретатора (Python/C) мгновенно делает процесс полноценным root. Critical
CAP_NET_RAW Создание RAW-сокетов (ping). Генерация произвольных пакетов, ARP Spoofing и прослушивание локального сетевого интерфейса в режиме Promiscuous. High
Защитный механизм PR_SET_NO_NEW_PRIVS

Системный вызов prctl(PR_SET_NO_NEW_PRIVS, 1, 0, 0, 0) указывает ядру Linux, что данный процесс и все его дочерние потомки ни при каких условиях не могут повысить привилегии (даже если они запускают исполняемый файл с битом SUID или расширенными Capabilities). Этот механизм является фундаментальной базой безопасности Docker и systemd.

3.2 Побег из контейнеров Docker: Механизмы Namespaces, Cgroups, Privileged Flags и Docker Socket

MITRE T1611 Container Breakout CLOUD INFRASTRUCTURE
Контейнеризация против Аппаратной виртуализации

Виртуальная машина (KVM, VMware, Hyper-V) запускает собственное независимое ядро поверх виртуального оборудования с аппаратной изоляцией (Intel VT-x, AMD-V, SLAT). Контейнер Docker делит одно общее монолитное ядро с хостовой операционной системой. Изоляция базируется на трех технологиях ядра Linux:

Технология изоляции ядра Назначение Объекты разграничения
Namespaces (Пространства имен) Ограничивает область видимости системных ресурсов для процесса. PID (процессы), NET (сетевые интерфейсы), MNT (точки монтирования ФС), IPC (память), UTS (имя хоста), USER (UID/GID mapping).
Control Groups (Cgroups) Ограничивает потребление ресурсов процессом. Лимиты CPU, оперативной памяти (RAM/Swap), дискового ввода-вывода (I/O) и числа процессов (pids.max).
LSM (Linux Security Modules) Мандатный контроль доступа поверх стандартных прав. Профили AppArmor, политики SELinux и фильтрация системных вызовов Seccomp (блокирует опасные syscalls: clone, mount, ptrace).
Вектор 1: Монтирование /var/run/docker.sock внутрь контейнера

Сокет docker.sock — это прямой канал управления демоном dockerd через протокол REST API (IPC сокет). Если непривилегированный контейнер имеет доступ к этому файлу сокета, атакующий отправляет команду демону хоста на запуск привилегированного контейнера-сателлита с монтированием всей файловой системы хоста:

docker run -v /:/host_root -it ubuntu chroot /host_root
Результат: Мгновенный выход в физический root хостовой машины!
Вектор 2: Флаг --privileged и побег через cgroups release_agent

Флаг --privileged отключает все барьеры изоляции:

  • Отключает Seccomp фильтрацию и AppArmor профиль.
  • Выдает процессу все возможные CAP_* (включая CAP_SYS_ADMIN).
  • Монтирует все системные устройства хоста в каталог /dev контейнера.

При наличии CAP_SYS_ADMIN атакующий внутри контейнера монтирует cgroup v1 контроллер, записывает команду шелла в файл хоста и регистрирует путь к нему в параметре release_agent ядра. При завершении дочернего процесса ядро хоста исполняет скрипт атакующего от имени root хостовой системы!

Добавьте секцию security_opt: [ "no-new-privileges:true" ] и используйте read_only: true для корневой файловой системы контейнера.
services: app: security_opt: - no-new-privileges:true read_only: true tmpfs: - /tmp

3.3 SUID/SGID, поведение динамического линковщика glibc (AT_SECURE) и PATH Hijacking

MITRE T1548.001 СИСТЕМНОЕ ПО
Семантика идентификаторов пользователя: RUID, EUID, SUID

Каждый процесс в Unix имеет 3 ключевых идентификатора пользователя:

  • RUID (Real UID): Реальный идентификатор пользователя, запустившего процесс.
  • EUID (Effective UID): Идентификатор, на основе которого ядро проверяет права доступа к файлам и системным вызовам в данный момент.
  • SUID (Saved UID): Сохраненный идентификатор, позволяющий процессам переключаться между непривилегированным и привилегированным состоянием.

Когда на исполняемом файле установлен специальный бит разрешения SUID (chmod u+s /path/binary), ядро при выполнении системного вызова execve() устанавливает EUID = владельцу файла (обычно root), независимо от того, кто запустил бинарник.

Безопасность glibc: Механизм AT_SECURE и переменные окружения

Почему нельзя просто подменить библиотеку через LD_PRELOAD=/tmp/evil.so для бинарника /usr/bin/passwd? Динамический линковщик ld.so при загрузке ELF-файла проверяет флаг ядра AT_SECURE (auxiliary vector). Если RUID != EUID, линковщик принудительно игнорирует все опасные переменные окружения: LD_PRELOAD, LD_LIBRARY_PATH, LD_AUDIT!

Механика уязвимости PATH Hijacking

Уязвимость возникает, когда программист в привилегированном C/C++ приложении вызывает системные команды без указания абсолютного пути:

system("curl -s http://internal.local/status"); // ОШИБКА!
// system() вызывает shell: /bin/sh -c "curl ..."
// Оболочка ищет утилиту curl слева направо по переменной $PATH!

Атакующий добавляет подконтрольный каталог в начало переменной PATH: export PATH=/tmp/evil:$PATH, создает исполняемый файл /tmp/evil/curl со своим шеллкодом. При запуске SUID-программы утилита curl запускается с правами root!

Команда аудита: find / -perm -4000 -type f 2>/dev/null.
char *args[] = {"/usr/bin/curl", "-s", "http://internal.local/status", NULL}; execv(args[0], args);

4.1 Протокол Kerberos V5 (RFC 4120): Архитектура билетов, структура PAC, Kerberoasting и AS-REP Roasting

MITRE T1558.003 ENTERPRISE AD
Трехфазная архитектура аутентификации Kerberos (RFC 4120)

Протокол Kerberos решает проблему безопасной взаимной аутентификации в недоверенной сети через доверенный центр распределения ключей (KDC — Key Distribution Center), функционирующий на контроллере домена (порт 88 TCP/UDP):

1
Authentication Service Exchange (AS-REQ / AS-REP): Клиент шифрует текущую временную метку (Timestamp) хэшем своего пароля (Pre-Authentication). KDC расшифровывает метку и возвращает TGT (Ticket Granting Ticket), зашифрованный секретным мастер-ключом служебного аккаунта krbtgt.
2
Ticket Granting Service Exchange (TGS-REQ / TGS-REP): Клиент предъявляет KDC свой TGT и запрашивает сервисный билет к конкретной службе с именем SPN (Service Principal Name), например MSSQLSvc/db01.corp.local:1433. KDC возвращает TGS-билет, зашифрованный хэшем пароля сервисной учетной записи!
3
Client / Server Exchange (AP-REQ / AP-REP): Клиент передает TGS целевому серверу. Сервер расшифровывает билет своим паролем и проверяет права доступа.
Структура Privilege Attribute Certificate (PAC)

В реализации Microsoft Kerberos билет содержит критическую структуру PAC. Она включает полный список идентификаторов безопасности (SID) доменных групп, в которых состоит пользователь (включая Domain Admins), а также две криптографические контрольные подписи:

  • Server Signature: Подписана хэшем пароля целевого сервиса.
  • KDC Signature: Подписана хэшем мастер-ключа krbtgt (защищает от нелегитимного повышения прав и подделки групп).
Сравнительный анализ Kerberoasting и AS-REP Roasting
Характеристика Kerberoasting (TGS Attack) AS-REP Roasting (AS Attack)
Необходимые привилегии Любой аутентифицированный пользователь домена. Вообще без учетной записи (нужно только знать имя логина).
Уязвимое условие Наличие у сервисной учетной записи зарегистрированного SPN. Выставленный флаг учетной записи: DONT_REQ_PREAUTH (Pre-authentication не требуется).
Тип перехватываемого тикета TGS-билет (шифрован паролем сервисного аккаунта). AS-REP ответ (зашифрован паролем целевого пользователя).
Режим перебора в Hashcat hashcat -m 13100 (Kerberos 5 TGS-REP etype 23). hashcat -m 18200 (Kerberos 5 AS-REP etype 23).
Архитектурная защита Переход на gMSA (Group Managed Service Accounts с 128-значными паролями) + отказ от RC4-HMAC. Включение обязательной предварительной аутентификации Kerberos для всех учетных записей.
Отследите поле Ticket Encryption Type: 0x17 (RC4-HMAC) при обращении к непривилегированным SPN.
EventID: 4769 AND TicketOptions: 0x40810000 AND TicketEncryptionType: 0x17 AND ServiceName != "*$"

4.2 Pass-the-Hash (PtH), протокол NTLM Challenge-Response и атаки NTLM Relay

MITRE T1550.002 WINDOWS AUTH
Математика протокола NTLM Challenge-Response

Протокол NTLMv2 основан на трехфазном рукопожатии:

1
Type 1 (Negotiate): Клиент объявляет серверу список поддерживаемых криптографических возможностей.
2
Type 2 (Challenge): Сервер генерирует случайную 8-байтную последовательность чисел — Server Challenge ($C$).
3
Type 3 (Authenticate): Клиент вычисляет хэш ответа: $R = \text{HMAC-MD5}(\text{NTLM\_Hash}, C \parallel \text{ClientChallenge})$ и отправляет серверу.

Фундаментальная причина Pass-the-Hash: Исходный пароль в открытом виде вообще никогда не используется в формуле! Входным параметром математической функции является сам NTLM-хэш (хэш MD4 от UTF-16LE строки пароля). Следовательно, для протокола NTLM знание хэша равносильно знанию самого пароля.

Механика NTLM Relay и обход цифровой подписи (SMB Signing)

Если клиент обращается к машине атакующего (например, в результате WPAD Spoofing или LLMNR/NBT-NS Poisoning), атакующий в режиме реального времени транслирует полученный Type 2 Challenge на третий корпоративный сервер (Exchange, LDAP, файловый сервер) и возвращает ответ клиента.

Защита:

  • Обязательная подпись SMBv2/v3 (SMB Signing): Сессия криптографически связывается с сессионным ключом. Подмена пакетов в канале невозможна.
  • Extended Protection for Authentication (EPA): Привязывает учетные данные к TLS-каналу сервера (Channel Binding Tokens).
  • Группа Protected Users: Запрещает кэширование NTLM хэшей в LSASS и принудительно переводит хосты только на Kerberos AES.
Политика: «Microsoft network server: Digitally sign communications (always)».
Computer Configuration -> Windows Settings -> Security Settings -> Local Policies -> Security Options: "Microsoft network client: Digitally sign communications (always)" = Enabled "Microsoft network server: Digitally sign communications (always)" = Enabled

4.3 Active Directory Certificate Services (AD CS): Мисконфигурации шаблонов сертификатов и атака ESC1

MITRE T1649 AD PKI ARCHITECTURE
Инфраструктура открытых ключей в Active Directory (PKI)

AD CS позволяет развернуть доменный Центр Сертификации (Enterprise CA), выпускающий сертификаты для шифрования, аутентификации пользователей и смарт-карт на базе шаблонов сертификатов (Certificate Templates).

Анатомия критической уязвимости ESC1

Шаблон сертификата становится уязвимым к мгновенной компрометации всего домена (ESC1), если одновременно выполняются 4 условия:

1
Права доступа (Enrollment Rights): Обычные пользователи (Domain Users / Authenticated Users) имеют право запрашивать сертификат по этому шаблону.
2
Флаг SAN (Subject Alternative Name): Включен флаг CT_FLAG_ENROLLEE_SUPPLIES_SUBJECT. Это разрешает заявителю самому указать, на чье имя выпустить сертификат!
3
Назначение (EKU — Extended Key Usage): Шаблон разрешает аутентификацию клиента (Client Authentication, Smartcard Logon или Any Purpose).
4
Утверждение менеджера: Выключено требование предварительного одобрения администратором (Manager Approval).

Эксплуатация: Обычный пользователь запрашивает сертификат, передавая в поле SAN имя Administrator@corp.local. Центр сертификации генерирует действительный сертификат. Атакующий использует сертификат для запроса доменного TGT-билета через Kerberos PKINIT (утилита Certipy / Rubeus) и становится Domain Admin!

Проверьте атрибут msPKI-Certificate-Name-Flag в объектах Active Directory.
# Поиск флага 0x00000001 (ENROLLEE_SUPPLIES_SUBJECT) Get-ADObject -Filter 'objectClass -eq "pKICertificateTemplate"' -SearchBase "CN=Certificate Templates,CN=Public Key Services,CN=Services,CN=Configuration,DC=corp,DC=local" -Properties * | Where-Object { $_."msPKI-Certificate-Name-Flag" -band 1 }

DFIR STANDARDS INCIDENT RESPONSE
Порядок сбора цифровых доказательств по энергозависимости (RFC 3227)

При расследовании инцидента первое правило судебного эксперта — не перезагружать и не выключать скомпрометированный сервер! По спецификации RFC 3227 (Order of Volatility) сбор артефактов производится от наиболее нестабильных носителей к долговечным:

1
Регистры и кэш процессора (CPU Registers & Cache): Уничтожаются за наносекунды при переключении контекста.
2
Таблицы маршрутизации, кэш ARP, таблица активных сетевых соединений в ядре.
3
Оперативная память (RAM): Содержит бестелесные шеллкоды, ключи шифрования, незашифрованные пароли и внедренные потоки.
4
Временные файловые системы (/tmp, pagefile.sys, hiberfil.sys).
5
Энергонезависимые накопители (SSD/HDD) и резервные архивные копии.
Анализ дампа оперативной памяти утилитой Volatility 3

Фреймворк Volatility парсит структуры ядра внутри бинарного дампа памяти (Raw memory image):

  • vol -f mem.raw windows.pslist: Выводит дерево процессов хоста.
  • vol -f mem.raw windows.malfind: Ищет участки памяти с флагами PAGE_EXECUTE_READWRITE (типичный признак внедрения шеллкода).
  • vol -f mem.raw windows.netscan: Восстанавливает сетевые сокеты и IP-адреса, открытые на момент создания дампа.
Используйте плагин windows.malfind с фильтром по PID.
vol -f memory_dump.raw windows.malfind --pid 1420
